# 1.7.4 全平台下载回归（2026-11-03）

## 结论

测试 12 个平台、20 组样例、39 条链接。Android 返回可用媒体 28/39；实际保存验收 16 个样例，15 个通过、Facebook 主样例 1 个失败。这里的“保存”包含系统下载目录导出和成品检查，不能与仅解析成功混为一谈。

X 视频/GIF 的主、备用链接又分别进行 3 轮新进程解析，共 12/12 通过；该结果仅代表本次网络出口和匿名会话的短期稳定性。

Windows 当前源码对照返回媒体 27/39，但其中两个 B站合集没有展开，按样例预期类型验收为 25/39。Windows 本轮没有实际保存、打包 EXE 或操作浏览器 GUI。

## 测试条件与边界

- Android 15 API35、x86_64 模拟器，1.7.4 Debug 业务代码及真实 Python/yt-dlp/FFmpeg 运行时；未连接物理手机。不是 ARM64 Release 真机验收。
- 所有平台均为匿名档案，没有使用或导出用户 Cookie。已登录账号、B站充电权益、付费内容与验证码后的访问仍未验收。
- 国内 Android 样例直连；海外样例通过宿主机已有 HTTP 系统代理建立临时测试通道。初始模拟器直连 YouTube 超时的结果另外保留，不拿它判定下载引擎坏掉。未修改用户手机或 Windows 应用的持久代理配置。
- 每组主、备用链接均解析；选择其中一个可行样例完成保存。视频选用较低或中等的实际格式来验证传输、音轨、成品与导出；不是 4K/8K 或所有编码的验收。合集只抽一集，没有下载数百集。超过 10 分钟且已有明确时长的主样例转用备用样例。
- 图文通过场景既保存一张图片，又保存该作品全部图片的 ZIP，并解码 ZIP 中的图片；不把平台返回的预览尺寸声称为完整原始尺寸或已验证无水印。
- 测试成品与任务临时目录在验收后清理。报告只保留错误摘要、ID、尺寸和字节数；完整分享链接仍保存在被 Git 忽略的私有测试数据中。

## 确认的问题与具体修复方向

1. **Instagram：固定移动 UA 干扰提取。** 在相同 URL、匿名状态、代理及其余 yt-dlp 元数据参数一致时，当前应用附加的 iPhone UA 返回 AUTH_REQUIRED；仅移除这个 UA 后返回同一作品和 12 个格式。修复方向是删除 YtDlpOptionsFactory 的 Instagram 固定 UA，让上游提取器管理请求身份，再对主、备用链接做解析和完整保存回归。
2. **Facebook：解析和下载间格式 ID 漂移。** 三次元数据请求指向同一视频，但首轮和次轮的 360p/720p/1080p 视频格式 ID 不同。当前仅 X 下载复用 MetadataSnapshots；Facebook 下载会重新提取，使用先前选中的 ID 因此可能报 QUALITY_UNAVAILABLE。修复方向是扩展现有快照下载机制，保留作品身份和清晰度意图；仅在源失效时刷新同一作品并重新匹配。
3. **快手：当前自动解析未通过。** 两条样例两端都没有取得有效视频源。原生入口还未像抖音/小红书那样接入传入的 cookieHeader，应在有效会话与浏览器响应下排查页面返回及会话传递；不应将风险响应直接归类为内容本身没有视频。
4. **Windows B站合集：只返回单集。** 同一两条链接 Android 可展开 158/165 集，Windows children=0。应同步分 P / ugc_season 展开与子集身份校验后再验收批量下载。
5. **访问限制单独处理。** YouTube 人机验证、抖音图文浏览器验证、小黑盒动态分享页，以及 Pixiv 备用 404 未在真实登录环境完成复测，不能通过改错误文字标成修复成功。
